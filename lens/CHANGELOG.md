# Changelog

## 1.5.1 — 2026-09-15

### Changed
- **Plugin-root `CLAUDE.md` renamed to `CONVENTIONS.md`.** Claude Code never loads a `CLAUDE.md` at a plugin root as project context, so the file was inert weight in the shipped payload and `claude plugin validate --strict` flagged it on every plugin. The content is unchanged — it is the internal conventions doc for developing this plugin — it just no longer claims a filename the runtime reserves for project context. `lens` now passes `claude plugin validate --strict` clean.

## 1.5.0 — 2026-07-31

- feat: new internal `lens:capability` skill (`user-invocable: false`, model-invocable, never in the `/` menu) reports the plugin version — read live from `.claude-plugin/plugin.json`, never hardcoded — the advertised `capabilities[]` token set, and `supports{}` (input keys, resolution rules, effort channel); an absent requested token returns a named-error miss instead of a silent no-op (the taxonomy is declared once in `engine-api.md` § Errors). Pinned in `test_capability.sh`: the manifest-sourced version read (a hardcoded semver anywhere in the skill fails the belt), the exact advertised token set, `supports{}`'s three slots, and both of the skill's returns. Backward-compat vs 1.4.3: purely additive — a brand-new skill, not a change to an existing one; a 1.4.3-only caller that never calls `lens:capability` sees no behavior change at all.
- feat: `lens:engine` accepts an additive `modelPolicy` arg (`{ deny?, default?, byRole?, byAgent? }`) resolving a per-dispatch model through the one precedence chain declared in `engine-api.md` § Model resolution, raising a named error when a denied value would otherwise win or when the policy is malformed. Malformation is judged **top-level type first** — a policy that is not an object (a stringified one, an array, a number, a bool) raises before any key is read, rather than being silently discarded along with the `deny` gate it carried; every other malformation rule is key-scoped and a keyless value would satisfy all of them. Pinned in `test_model_policy.sh`, ordering included. Backward-compat vs 1.4.3: absent `modelPolicy` (or `{}`) never raises and resolves through the same frontmatter/harness defaults 1.4.3 always used — byte-identical; `null` and an absent key stay "not provided" and are not a wrong type, so the gate is unreachable from a 1.4.3-shaped call.
- feat: `lens:engine` accepts an additive `verifyVotes` arg (integer 1–5, default 1) driving the named rule `huginn-quorum-v1` (`quorum = ceil(n/2)`) — one voting rule every VERIFY run goes through, whether one skeptic votes or five. Pinned in `test_verify_votes.sh`: the arg's declared integer shape and its 1–5 range, its default of 1, the pre-flight range check that rejects a panel size outside it, and the rule name the row must carry. Backward-compat vs 1.4.3: absent `verifyVotes` ⇒ n=1 ⇒ the same quorum rule collapses to exactly 1.4.3's unanimous-drop-on-refute outcome in all three outcome branches, through one universal code path — a reduction of 1.4.3's behavior, not a special case bolted alongside it.
- feat: the Tier-3 finder record (both the call-time `injectedFinders` form and the file-registered `finders:` form) gains optional `model` / `effort` keys — `effort` is a prompt-level directive, one of `low` | `medium` | `high` | `xhigh` | `max`. Backward-compat vs 1.4.3: both keys are optional on both forms; a record naming neither resolves and dispatches exactly as it did in 1.4.3. A malformed `model`/`effort` on the file-registered form degrades (`degradedReasons: finder-malformed`) rather than raising, so standalone `/lens:review` cannot fail on project config; the identical malformation on a call-time `injectedFinders` record raises a named error — a deliberate asymmetry, not an inconsistency. Pinned in `test_injected_finders.sh`: both keys declared optional on each form's own record-shape cell, `effort`'s five accepted values checked in both directions, and each half of the degrade-vs-raise split pinned on the form that governs it.
- feat: `lens:engine`'s return gains an optional top-level `degradedReasons[]` (closed 7-code enum, paired 1:1 with `degraded:true`) — the release's one new **top-level** return field; `degraded` (bool), `summary` (prose), `emptyScope`, and `adherence` are unchanged. The 1:1 pairing is **enforced by the schema, not only asserted in prose**: each entry requires its `code` and admits no key outside `code` and `detail`, and the success branch carries the biconditional as a pair of conditional clauses, so `degraded:true` with no reasons and `degraded:false` with a non-empty array both fail validation. Pinned in `test_engine_api.sh`: the one returns-table row it may occupy, its code list checked in both directions against the schema's enum, and each of the seven codes tied to the governing rule site that emits it — plus the reverse sweep, that every `degraded: true` instruction under `lens/` names the code it sets. `finder-malformed` is the one code with three emitting sites (a file-registered record rejected in pre-flight, a finder's output rejected at Step 4, an adapter's output that could not be normalized), so its `detail` must name which one produced it — the set stays closed at seven rather than splitting. **Backward-compat vs 1.4.3: the FIELD is additive, but the biconditional is a NARROWING — read that as breaking, not as the same class of change as 1.1.0's `emptyScope` or 1.4.0's `adherence`.** Those two were optional additions that could not invalidate a document already valid; this one can, and does: `degradedReasons` did not exist in 1.4.3, so **no 1.4.3-produced return carrying `degraded: true` validates against the 1.5.0 schema** — every one of them is now schema-invalid, and a `degraded: false` return carrying a stray empty-vs-populated array is judged too. This matters to exactly one caller shape: a consumer holding **prior-run state** (a `.claude/lens/review-state.json`, a stored `priorFindings`, a vicario-produced document) and validating it against the shipped schema. Such a caller must **backfill** a `degradedReasons[]` entry onto any stored `degraded: true` document, or **skip validation** of prior-run state and validate only what this engine returns. Nothing is renamed, re-typed or removed — the break is a new cross-field constraint, not a field change.
- feat: the per-finding record gains two optional fields from the same quorum wiring — `voteResolution` (`verified` | `abstained`, that finding's outcome under `huginn-quorum-v1`) and `votes.abstained` (the dead-vote tally the rule reads; the procedure stays declared at `pipeline.md` §5). `verified` and the three 1.4.3 `votes` keys keep their meaning, and no field is renamed, re-typed, or removed. Backward-compat vs 1.4.3: field-additive as well — but unlike `degradedReasons[]` these two ride the ordinary path, so a caller that passes none of the new inputs (n=1, never degraded) still receives them. `degradedReasons[]`, `voteResolution`, and `votes.abstained` are the **complete** set of fields the return gains: it is **not byte-identical** to 1.4.3's. A consumer that reads only the fields it knows is unaffected; one that asserts an exact key set must widen it.
- feat: the `verifier` role carries a **never-Haiku floor** — a second gate alongside `modelPolicy.deny`, declared and applied with the rest of the model plan in pre-flight (`engine-api.md` § Model resolution), and pinned by `test_model_policy.sh` (its matching rule, its raise, where it is applied, and its verifier-only scope). A policy value that would resolve the adversarial skeptic below it raises the same named error a denied winner does, rather than silently downgrading the pass that decides which findings survive; `finder`-role dispatches are gated by `deny` alone, so a caller that wants cheap finders still gets them. Backward-compat vs 1.4.3: unreachable without `modelPolicy` — with no policy the verifier resolves to its own `model: opus` frontmatter exactly as in 1.4.3, so a 1.4.3-shaped call can never meet the floor.
- feat: `lens:capability`'s `require` is validated for shape before it is matched — not an array of strings ⇒ the same named-error envelope the engine returns for a malformed 1.5.0 input, under the same code, `E_INVALID_INPUT` (the registry is closed at four, and `engine-api.md` § Errors stays its one declared home); the shape gate and the manifest read are both pinned by `test_capability.sh`. A caller that stringified its config gets its real bug back instead of a false-green report or a miss naming single characters. The manifest read asserts `.version`'s JSON **type inside `jq`**, asks inside the same filter that the value carry at least one non-whitespace character, trims the surrounding whitespace there, and takes `-e` — so an absent, wrong-typed, empty **or whitespace-only** `.version`, and a truncated manifest, surface as an install-integrity failure with a code of its own, carrying the path that failed and the exit status that classified it, instead of exiting 0 with a fabricated version. Neither test can be moved after the read: `-r` prints an unquoted number and a quoted string identically, and a padded value clears every post-hoc check a healthy one clears while reporting a version no caller's comparison will match. The trim is the read's one normalization and is declared as such — "verbatim" means the filter's output, not the manifest's raw bytes. That failure travels the **same `error` branch key** as every other one, so a caller doing the documented `if (r.error)` test can never land in the success arm holding an undefined `version` — reported as prose it had no `error` key for that branch to see. Backward-compat vs 1.4.3: no surface at all in 1.4.3 — `lens:capability` is new in this release.
- feat: `lens:engine`'s return is declared on **two channels** — the ordinary `review-findings` object and the pre-flight named-error envelope — told apart by the presence of a top-level `error`, the same branch key `lens:capability` already uses. `review-findings.schema.json` declares them as a top-level `oneOf`, so a raise is schema-valid on its own sealed branch instead of arriving as a schema-invalid object on an undeclared channel; the success branch keeps its required set (`findings`, `recommendedEscalation`, `degraded`) and its seven-field shape untouched, because the envelope is a branch rather than an eighth field. The registry a consumer branches on is closed at **four**, and this is the release note that names them so a caller can write the branch: `E_INVALID_INPUT`, `E_MODEL_POLICY_UNSATISFIABLE`, `E_UNSUPPORTED_CAPABILITY`, `E_MANIFEST_UNREADABLE`. Their raisers, triggers and per-code `extra` shapes live in `engine-api.md` § Errors and are not restated here — naming four strings is disclosure; a table of raisers and triggers would be a second registry. The four spellings are also mirrored into `review-findings.schema.json`'s envelope as a closed enum, so an invented code fails validation instead of riding through as a bare string, and `test_schema_types.sh` pins that mirror back against the § Errors table. Pinned in `test_engine_api.sh` (the declared channels, the branch key, and that the envelope never inflates the derived success field set) and `test_schema_types.sh` (the two branches and the sealed envelope). Backward-compat vs 1.4.3: the failure channel is reachable only through a 1.5.0 input (`engine-api.md` § Errors, I-2), so a 1.4.3-shaped call receives the success channel and can receive nothing else; a consumer that validates every return against the schema must branch on `error` first.
- fix: `pipeline.md` §5's v1 "unanimous-drop" paragraph — "Wiring multi-skeptic voting … is deferred" — is retired now that `huginn-quorum-v1` is wired, with no behavior change at n=1. It is one of **three** non-additive edits in this release, not the only one: the other two are `engine-api.md` § Model resolution losing its unreachable ⑥–⑦ substitution row (see below) and the schema's cross-field narrowings (see below).
- **note: what this release NARROWS.** Three constraints reject documents the 1.4.3 schema accepted, and all three are cross-field rules rather than field changes — nothing is renamed, re-typed or removed. (1) `degraded: true` now requires a non-empty `degradedReasons[]`, and `degraded: false` forbids a populated one; since `degradedReasons` did not exist in 1.4.3, **no 1.4.3-produced degraded return validates**. (2) `emptyScope: true` now requires an empty `findings[]` — the flag is declared the sole nothing-to-review discriminator, and a document setting it beside findings contradicted the array it replaces; `emptyScope` shipped in 1.1.0, so a stored one can be affected. (3) the `votes` counts now carry `minimum: 0` — `total`, `couldNotRefute` and `refuted`, the three that predate this release — and `votes.total` is additionally bounded to `verifyVotes`' own `1..5`, so a negative member or an out-of-range panel size is rejected; `votes` shipped **unbounded in 1.0.0**, not in 1.4.3, so every release from 1.0.0 onward produced documents this clause can reject. Who this reaches: a consumer that **validates prior-run state** — a stored `priorFindings`, `.claude/lens/review-state.json`, or a vicario-produced document — against the shipped schema. Such a caller must backfill the missing field, or validate only what this engine returns and skip validation of prior-run state. A consumer that merely *reads* fields is unaffected.
- fix: `engine-api.md` § Model resolution's denied-winner rule is **two** branches, not three. A denied winner from chain positions ②–⑤ raises; a denied winner from ⑥–⑦ raises. The retired third row substituted "the highest-precedence allowed policy value" for a denied implicit default — but ③–⑤ are consulted before ⑥–⑦ and are matched to the dispatch site, so a dispatch that reaches ⑥–⑦ is one the policy was silent about there and the substitute set is empty by construction: the row could never fire. `deny` is also stated as what it is — a gate on the winner, never a filter over the candidates — because under the filter reading a denied value never wins and the ②–⑤ raise, this code's primary documented trigger, would itself be unreachable. Non-additive: a caller that read the substitute row as a promise now gets a raise, which is what the run already did. Pinned in `test_model_policy.sh`, including a negative that the retired row cannot come back.
- note: three new belts pin this release's contract — `test_capability.sh` (the 11 `capabilities[]` tokens, the 8 `supports.inputKeys[]`, the 5 resolution rules, both returns, `require`'s shape gate, and the type-asserting manifest read), `test_model_policy.sh` (the top-level type gate and its ordering ahead of the key rules, the four-key shape, the one precedence chain, the denied-winner rule, and the verifier's never-Haiku floor), and `test_verify_votes.sh` (`huginn-quorum-v1`'s three branches proved executably across all three fixtures, including the n=1 reduction). Three existing belts carry the rest: `test_engine_api.sh` (the two return channels, and `degradedReasons[]` — its single returns-table row, its seven codes checked both ways against the schema enum, and each code's governing site), `test_schema_types.sh` (the two channels again at the schema, `degradedReasons[]`'s array shape and optionality, and the per-finding pair — `votes`' exact four keys with `abstained` typed among them, and `voteResolution`'s exact two-value enum, both optional), and `test_injected_finders.sh` (the Tier-3 record's optional `model` / `effort` keys on both forms, `effort`'s five values, and the degrade-vs-raise split). Two further belts land alongside them: `test_capability.sh` grew an executable manifest read over ten synthetic manifests (missing, a directory, unreadable, malformed, empty, whitespace-only, wrong-typed, multi-document, whitespace-padded, and valid) and `test_model_policy.sh` grew an executable `lens-model-precedence-v1` matrix, so the two densest rules in this release are proved by running them rather than by grepping the prose that states them; and a new `tests/lib/test_belt_helpers.sh` unit-tests the shared `flatten()` / `one_line()` selector helpers those belts depend on, running `one_line()` against a deliberately multi-line input and asserting it FAILS — the guard written to catch always-true selectors had no test proving it was not one itself. The suite runs **55** belts.
- note: **compatible on the INPUT surface, narrowed on the RETURN surface — those are different answers and this entry gives both.** Every new input is additive and optional, so a call that passes none of them takes exactly the paths 1.4.3 took and can receive no error envelope (I-2); what comes back is *not* identical, per the exhaustive field list carried by the per-finding `voteResolution` / `votes.abstained` bullet above, and validating a 1.4.3-era document against the shipped schema is a separate question again — see the **narrowings** note above, the one that enumerates all three. **matali is not a clean backward-compat bar.** matali's `review` skill instructs passing a `modelPolicy` "through verbatim", and the value it forwards is a role→model map keyed `cheap`/`fix`/`judge`/`verify`/`worker`. lens 1.5.0 accepts exactly `{ deny, default, byRole, byAgent }`, so that call is rejected in pre-flight and dispatches zero finders. The rejection is correct and deliberate — a silently discarded policy would take the `deny` gate down with it while the run still reported an ordinary success — so the fix belongs on the matali↔lens bridge, which must translate that map into `byRole`/`byAgent` or omit the key before matali consumes 1.5.0. matali lives in its own repo, so the work is tracked in `.claude/drift-queue.json` rather than done here.
